# Test fixes A3-A6 (16 Oct phone test)

Order: A3, A4, A5, A6. One commit each on `hermes/test-fixes-a3-a6`. A1 (sign-in), A2 (server device list) and A7 (type_text) are separate and not in this run.

## A3 - "Back to <app>" must never name the keyboard
Bug: after typing a prompt in the Claude app, the control bar said "Back to Gboard". The target is recorded from TYPE_WINDOW_STATE_CHANGED (McpAccessibilityService.kt ~414-424) through isForeignWindowStateChange (~827-833), whose TYPE_APPLICATION check passes when the window type can't be resolved (null).
1. isForeignWindowStateChange: when the window type is null (unresolvable), return false, so the tracked app is not updated.
2. Where the target is recorded, also never record: our own package, `com.android.systemui`, or the package of any enabled input method (InputMethodManager.getEnabledInputMethodList(), packageName). Put this in a small pure function taking (packageName, ownPackage, imePackages) so it can be unit tested. Read the input method list when the check runs (it changes rarely; no caching needed).
3. Do not change CurrentForegroundAppProviderImpl or anything else that reports the foreground app to tools. If the back-to target turns out to come from CurrentForegroundAppProviderImpl rather than the recording path above, STOP and report.
4. Tests: null window type gives false; an input method package with TYPE_APPLICATION gives false; systemui and our own package give false; a normal app with TYPE_APPLICATION gives true.

## A4 - accessibility permission: re-enable prompt and one-tap pause
Some apps (Viettel Tammi; likely many banking apps) refuse to open while any accessibility service is on. And when the service is off, Home's PermissionWarningCard (HomeScreen.kt ~105-108, 160-163) only goes to the Permissions screen.
1. Re-enable: the PermissionWarningCard's action opens our service's own settings page directly. Build the intent in a pure, testable function: on API 31+ use Settings.ACTION_ACCESSIBILITY_DETAILS_SETTINGS with Intent.EXTRA_COMPONENT_NAME = our service's ComponentName; below 31, or if starting it throws ActivityNotFoundException, fall back to Settings.ACTION_ACCESSIBILITY_SETTINGS with extra ":settings:fragment_args_key" = the flattened component name and extra ":settings:show_fragment_args" = a Bundle holding the same key and value. Reuse PermissionUtils (~line 50) for the plain intent. Keep the card's existing text.
2. Pause: on Home, directly under the status indicator, a text button "Pause permission", shown only while the service is on. Tapping it shows a dialog: title "Pause accessibility permission?", body "Some apps, like banking apps, won't open while it's on. Your AI can't use this phone until you turn it back on.", buttons "Pause" and "Cancel". "Pause" calls disableSelf() on the running McpAccessibilityService, then refreshes the permission status (MainViewModel.refreshPermissionStatus) so the warning card from step 1 appears straight away. Reach the service through the existing way the app reaches it; if none exists, add a static reference set in onServiceConnected and cleared in onUnbind and onDestroy. If the service isn't running, the button is hidden.
3. Tests: the intent builder for API 31+ and below 31 (action and extras); the view-model or helper logic that decides whether the pause button shows.

## A5 - launch_app waits until the app is in front
Bug: Firefox once stayed in the background. AppManagerImpl.openApp (~18-44) reports success right after startActivity.
1. After startActivity, poll the current foreground package (the same source wait_until uses) every 100 ms for up to 5000 ms. If it matches the requested package, succeed.
2. If not, call startActivity once more with the same intent and poll for up to 3000 ms more. If it matches, succeed.
3. Otherwise return the step's existing failure result with the message "<package> did not come to the front; <foreground package or unknown> is in front". Use an existing error code; if a new one would be needed, use the existing generic failure and name it in your report. No protocol change.
4. Do the waiting in whichever layer is already a suspend function (openApp or its caller in StepDispatcher).
5. Tests with a fake foreground source and virtual time (runTest): in front at once gives success and one start; in front only after the retry gives success and two starts; never gives failure, two starts and the message above.

## A6 - connection heartbeat, so "Connected" is true
Bug: Home showed a green "Connected" while the server had lost the phone. The status comes only from the local TransportStatus (DeviceTransportClient.kt ~330, HomeStatusIndicator.kt ~66-76) and nothing checks the socket is alive.
1. If the device WebSocket uses OkHttp, set pingInterval to 30 seconds on the OkHttpClient used for it. OkHttp then fails the socket when a pong doesn't come back, which must go through the existing failure and reconnect path, so the status leaves Connected. The server (Node `ws`) answers pings automatically; no server change.
2. Check that the existing failure path sets the status away from Connected and schedules a reconnect; if it doesn't, make it do so with the smallest change.
3. If the WebSocket isn't OkHttp, STOP and report which library it is.
4. Tests: the client is built with a 30 s ping interval; a socket failure moves the status from Connected to the reconnecting state.
