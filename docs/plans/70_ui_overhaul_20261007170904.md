# Plan 70 — UI overhaul (Home redesign, AI clients, connector onboarding, Event Channel removal)

**Companion plan**: `droidthumb-server` plan 05 (same timestamp) covers the server-side pieces this
plan's screens read from: account-level AI client display name/image (its `account_connection
_overrides` table + rename route), flow run counts for ordering, and the account device limit (a
plain `accounts.device_limit` column, no new devices table — device added-at date needs no new
column at all, since `devices.created_at` already exists). Build that plan's User Story 1 before
this plan's User Story 3 (AI clients list) and User Story 4 (rename), and its User Story 3 before
this plan's Task 3.5 (this device). Plan 05's User Story 2 (flow run counts) is the one piece
plan 05 itself recommends splitting into its own, separately-reviewed plan rather than building
inline — this plan's Task 3.4 (Saved flows) depends on whichever plan ends up building that, so
Task 3.4 cannot start until that dependency — wherever it lands — ships.

**Mockups (for approval before building)**: every new/changed screen in this plan has a working,
clickable mockup at https://claude.ai/artifact/AodppMdn127yDLWNkiVLQh (Home → AI client detail →
Add AI client → per-client instructions all link through; Settings and About are static). Colors,
spacing, copy and exact layout in that artifact are what's under review — the Compose code in this
plan's actions implements the APPROVED version of it, so a few actions below describe structure and
state handling precisely but leave final spacing/copy as "per the approved mockup" rather than
pre-committing pixel values that review may change. Everything else (deletions, data models, server
contracts, navigation) is fully specified now.

**Open questions — need your answer before Task 3.4 (connector URL / regenerate) and Task 9.1
(device limit) can be finalized:**
1. `TransportStatusCard`'s existing "Connector URL" + "Regenerate" feature (the per-device secret
   URL used by self-host/legacy auth) isn't mentioned in your spec. The new "Add AI client" →
   per-client instructions screens show a "Your MCP server URL" copy box — is that the SAME
   connector URL, just relocated there, with "Regenerate" also moving there (e.g. onto each AI
   client's detail page, or a new "Regenerate server URL" entry in Settings)? Or does account-mode
   auth replace the need for a device-level secret URL entirely for hosted deployments, and this
   whole mechanism becomes self-host-only (and so moves under Settings, not the Home screen)?
2. Device limit (free tier) — is there an actual number yet, or does "This device" → "+ Devices"
   just always go to the install page until a limit is decided elsewhere? Plan 05 adds the column
   either way; this only affects whether Task 9.1's branch is reachable yet.

**Resolved (founder, 2026-10-07):**
1. Connector URL/Regenerate: account-mode auth replaces the need for a device-level secret URL for
   hosted deployments entirely. This mechanism is self-host-only and gets NO Home/Settings surface
   in this plan — Task 2.1 deletes `TransportStatusCard`'s connector-URL/regenerate UI in full
   alongside the host/port/TLS fields. The underlying `ConnectorUrlSettings`/registration flow stays
   (self-host mode still needs the secret to authenticate), just with no in-app way to view/
   regenerate it for now — out of scope here, not re-litigated.
2. Device limit: no number yet. `device_limit` stays always `null`/unenforced (already built this
   way server-side); "+ Devices" always opens the install page — the multi-device sales-page branch
   stays unreachable until a real number exists.
3. Pause (raised during US3 implementation — the approved mockup's status card only renders a
   "Resume" button when paused, with no "Pause" affordance for the other three states): tapping the
   status indicator in any non-paused state opens the same Pause-options dialog (1 hour / until
   tomorrow / until I resume) the old `TransportStatusCard` already had — no new UI chrome, Home's
   status pill is the sole entry point.
4. AI client detail's "Change image" (raised during US4 implementation): the device photo picker was
   the first choice, but `droidthumb-server` has no image-hosting infrastructure at all today —
   `SPACES_*` only backs up Postgres via a bash script, there is no upload endpoint or app-facing
   storage client. Building that for real is a sub-feature of its own (upload route, validation, a
   new/reused Spaces bucket, client-side upload wiring). Deferred for this round: "Change image" is
   a disabled button with a "Coming soon" note, same deferral pattern as "remove connection".

hosted-app release pipeline (tag-triggered draft releases / the rolling edge release), which a
self-hoster has no reason to use — a self-host build is produced locally or via `ci.yml`'s
`build-release` job, documented in `docs/build-notes.md`.
