# Tool-surface mapping — the fork's 57 MCP tools vs. the closed step vocabulary (§7.2)

**Status:** read-only research. No code changed. This answers R-13 in the design doc (`droidthumb-server/docs/droidthumb-design-doc(1).md`, v0.6 — the untracked draft that already carries D-20/D-21/D-22 and the corrected tool count; the tracked v0.5 file is stale and does not have these): *"which of the fork's 57 tools survive into the closed step vocabulary — the largest open question and the next one to answer."* Sources: design doc §7.1–§7.4, D-09, D-10, D-21, B-11's Play note (lines 363–450, 415, 148–154 of the v0.6 draft); `droidthumb-android/docs/MCP_TOOLS.md` (all 57 tools, line numbers cited per tool below); `droidthumb-android/docs/module-map.md` for what D-19 removes.

**A note on §7.2's op count.** The task frame assumes §7.2 currently has 18 ops. Counting the table's own rows (one row = one line in the §7.2 table, some rows list 2–3 alternative `op` strings sharing one parameter shape) gives **17**: `launch_app`, `open_intent`, `tap`/`long_press`, `swipe`/`scroll_find`, `type_text`, `key`, `wait`, `wait_until`, `read`, `assert`, `if_visible`/`else`/`end`, `if_var`/`switch`, `retry`, `call_flow`, `request_draft`, `snapshot`, `pause`. If every slash-separated alternative is instead counted as its own distinct `op` string, the count is 22. Design doc is silent on which reading is intended — I use the 17-row count as the baseline below and flag both numbers in the closing section.

### 2. Minimum new ops to preserve all 57 capabilities

Two different kinds of protocol growth are being conflated by the phrase "new op," so I separate them:

**A. Parameter/enum extensions to existing ops** (no new `op` string; existing message shape, larger JSON Schema):
- `key`: enum grows to include `dismiss_keyboard`, `delete_char`.
- `tap` (selector variant): add optional `mode: "node_action" | "gesture"`.
- `swipe`/`scroll_find`: add an alternate point-to-point mode (`from:{x,y}`, `to:{x,y}`, `duration_ms`) alongside the existing directional mode; add optional `amount` (`small`/`medium`/`large`) and `variance_pct` to the directional mode.
- `type_text`: add optional `offset` (cursor position) and optional `search` (find-and-replace mode).
- `open_intent`: add optional `data` (URI string).

**B. Genuinely new `op` strings** the device executor has to learn:
1. `double_tap` — `{ selector? , at?: {x,y} }` (mirrors `tap`/`long_press`'s shape)
2. `clipboard` — `{ mode: "get" | "set", text?: string, capture?: string }` (`text` required when `mode:"set"`; `capture` required when `mode:"get"`)
3. `wait_idle` — `{ timeout_ms: number, match_percentage?: number }` (default 100)
4. `close_app` — `{ package: string }`
5. `camera_capture` — `{ camera_id?: string, resolution?: string, quality?: number, flash_mode?: string, capture: string }` (output is a file reference per D-21, not inline bytes by default)

**Resulting op count:** baseline 17 (row-count reading) → **22** with the 5 new op names added (the parameter extensions in (A) don't change this count, since they grow existing rows rather than adding new ones). Under the alternative 22-token reading of the baseline (counting `else`/`end`/`switch` etc. as their own op values), the total would be **27**.

Everything currently LATER or DROP is deliberately excluded from this minimum set — "preserve all 57" as asked is a different, larger question than "what does v0 need," and the LATER/DROP tools above are exactly the ones I don't think earn a place in the closed vocabulary yet (or, for the DROP five, ever, per D-09 and the design doc's own stated recommendation for the two Sharing tools).

### 3. Cost of each proposed new op

| New op | Breaks D-09's "stranger-safe" property? | Breaks Play replay-only (B-11)? | Protocol changes beyond adding the op? |
|---|---|---|---|
| `double_tap` | No — same bounded coordinate/selector risk profile as `tap` | No — deterministic action, no branching | No |
| `clipboard` | Not structurally, but `mode:"get"` can capture sensitive text (e.g. a just-copied password) into a run report — needs the same SEC-08 redaction-at-capture treatment as any other captured variable; a policy note, not a vocabulary problem | No | No |
| `wait_idle` | No — read-only, no side effect | No | No — reuses the existing `TreeFingerprint` machinery (`mcp/tools/TreeFingerprint.kt`, per module-map) |
| `close_app` | No — bounded to one named package, no code execution | No — deterministic | No, but the executor must preserve and surface the underlying "background apps only" limitation as a step precondition, or a flow author will get silent no-ops on foreground kills |
| `camera_capture` | **Borderline.** Camera access is a materially different trust proposition than tap/type — a stranger's shared flow that silently photographs whatever the phone is pointed at is not the same risk class as one that taps buttons. Still typed/bounded (not scripting), so it doesn't break D-09's *sandboxing* property, but it does stretch the "safe to download and run" assumption furthest of anything proposed here | Probably not under B-11's literal text (a flow-triggered photo capture is still deterministic, not "autonomous decision-making"), but Camera permission draws its own, separate Play Console review scrutiny regardless of the accessibility-specific policy — a second layer of Play risk beyond SEC-21 | **Yes.** This op is gated on D-21's file-reference plumbing actually existing (inline-vs-signed-URL), since a captured photo is exactly the payload-size case D-21 was designed for. It is not a "just add an op" change |
| `open_intent` + `data` | No — still one bounded string parameter, no scripting | No | No — D-06 already sanctions intent-shortcut navigation; this only broadens which intents can be named |
| `type_text` + `offset`/`search` | No | No | No |
| `swipe`/`scroll_find` extensions | No | No | No |
| `key` enum growth (`dismiss_keyboard`, `delete_char`) | No | No | No |
| `tap` + `mode` | No | No | No |

The pattern: every extension is cheap except `camera_capture`, which is the one place where "add an op" quietly means "also finish implementing D-21 first."

### 4. Five recommendations I'm least sure of, and what would settle each

1. **`android_press_key`'s `DEL` → `key:delete_char` vs. a `type_text` "backspace N" mode.** I picked extending `key` for symmetry with the other global-action-shaped keys, but DEL actually acts on focused-field text, not a global action. Settling this needs real live-authoring tool-call logs (D-10: "the authoring session's tool-call log *is* the flow") showing which shape Claude actually reaches for when fixing a typo — not available until live authoring exists.
2. **One `clipboard` op with a `mode` switch vs. two separate `clipboard_get`/`clipboard_set` ops.** Most of §7.2 is single-purpose per op; a mode switch is a minor precedent break. This is a style call for whoever writes `droidthumb-protocol`'s JSON Schema (D-16), not something either document currently in front of me settles.
3. **Whether Google Play would actually accept `camera_capture` in the Play replay-only flavour.** B-11's policy text is about the *AccessibilityService* API specifically; I don't know whether Play's general Camera-permission review would treat a deterministic photo-capture step differently in practice. This needs an actual Play Console policy determination (or a documented precedent app), not something derivable from either document.
4. **Whether `write_file`/`append_file`/`file_replace`/`delete_file` should stay LATER-with-a-path-forward or become permanent DROPs like `download_from_url`.** I distinguished them from `download_from_url` on the theory that SAF's per-location user consent is an adequate trust gate even for a stranger's shared flow, but neither document has actually threat-modeled "a downloaded flow writes to a location I already granted" — R-13 flags the *mapping* gap, not this *trust* question. A real threat-modeling pass would settle it.
5. **`android_scroll_to_node` mapping cleanly onto `scroll_find` despite the missing auto-direction-detection.** I assumed a flow author already knows the scroll direction because they scrolled manually during the live-authoring session that produced the flow. This breaks for a dynamically-reordering list where the target moves between authoring and replay. A recorded-tree fixture test exercising `scroll_find` against a reordering list (the kind of thing `selector-engine`'s "JVM with recorded tree fixtures" testing tier, §6.1, is built for) would settle whether this is a real problem or a non-issue.
